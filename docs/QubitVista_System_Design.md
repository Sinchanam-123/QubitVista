# QubitVista — System Design & Methodology

**Final-year major project · 2025–26**

A browser-based single-qubit quantum circuit simulator built for teaching, not for
research-grade computation. This document covers the system design, the methodology behind it,
and the full implementation detail of both halves.

| | |
|---|---|
| Phase | 1 of 2 |
| Qubits | 1 |
| Gate set | 13 |
| Golden circuits | 104 |
| Verified snapshots | 359 |
| API routes | 8 |

---

## 1. Problem & objectives

Existing quantum simulators show a learner the *answer*: run a circuit, get a final state. The
gap this project addresses is the absence of **step-by-step state evolution** — the ability to
watch a qubit move one gate at a time, seeing the Bloch vector rotate, the amplitudes turn in the
complex plane, and the measurement probabilities shift as each gate is applied.

That single capability is the project's central contribution. Everything else in the design
exists to deliver it or to prove it correct.

### The six concepts Phase 1 teaches

| Concept | Demonstrated by | What the backend must expose |
|---|---|---|
| State evolution | Any multi-gate circuit, stepped through | Per-step snapshots + rotation axis/angle |
| Superposition | `H` on \|0⟩ → \|+⟩ | Bloch vector pole → equator; 50/50 probabilities |
| Phase | `Z S T RZ P` | Complex amplitudes with magnitude *and* phase angle |
| Interference | `H → RZ(θ) → H` | Per-step amplitudes showing cancellation |
| Measurement | `RY(θ)` | All basis-state probabilities, every step |
| Reversibility | `S,S†` · `T,T†` · `H,H` | Final snapshot identical to `steps[0]` |

Three further properties fall out of the same step sequence rather than needing features of their
own: **unitarity** (probabilities sum to 1 at every step), **determinism** (evolution between
measurements is fully predictable), and **continuity** (the state traces an arc, it never
teleports).

## 2. System architecture

Three tiers with one hard rule between them: **no quantum logic in route handlers, and no
web-framework imports in the engine**. The engine is a pure function — gates in, dictionaries out
— which is what makes it testable and runnable without a server, and what allows a second
independent implementation to be checked against the same data.

```
PRESENTATION  +------------------------------------------------------+
              |  Browser - React 18 + Vite                           |
              |  Simulator . Learn . Home . About . Exit             |
              |  Canvas 2D (Bloch) . Plotly (charts) . SVG (dials)   |
              +------------------------------------------------------+
                    |  POST /api/simulate        ^  steps[]
                    |  full gate list            |  one snapshot per gate
                    v                            |
API           +------------------------------------------------------+
              |  FastAPI - main.py                                   |
              |  8 routes . Pydantic v2 . CORS . stateless           |
              +------------------------------------------------------+
                    |  plain dicts, no framework types
                    v
SIMULATION    +---------------------------+  +---------------------------+
              | quantum_engine.py         |  | engine_ref.py             |
              | production . Qiskit       |  | independent reimplementation
              | Statevector, exact        |  | never imported by the app |
              +---------------------------+  +---------------------------+
                    ^  verifies                 ^  verifies
                    +-------------+-------------+
              +------------------------------------------------------+
              | circuits_spec.json - 104 circuits, 359 snapshots      |
              | generated by Qiskit, checked against Rodrigues        |
              +------------------------------------------------------+
```

**Two engines, on purpose.** The API imports only `quantum_engine`. `engine_ref` is a
deliberately separate implementation that the conformance harness uses as its default target, so
the golden data can be checked without the production code. Keeping two independent
implementations agreeing on 359 snapshots is the point — they are never merged and never import
each other.

### Technology choices

| Layer | Choice | Why this one |
|---|---|---|
| Simulation | Qiskit 2.2.3 | Industry-standard; `Statevector` gives exact analytic results with no sampling noise |
| API | FastAPI | Automatic OpenAPI docs at `/docs` make the backend testable before any frontend exists |
| Validation | Pydantic v2 | Arrives with FastAPI; rejects malformed circuits before they reach the engine |
| UI | React 18 + Vite 5 | Component model suits per-step re-rendering; Vite gives sub-second HMR |
| Bloch sphere | Canvas 2D | Full control of depth-sorted wireframe and rotation arcs at a fraction of WebGL's weight |
| Charts | Plotly | Used on the landing page's live demo |
| Routing | React Router 6 | Five routes, and deep links that carry a circuit into the simulator |

## 3. Request lifecycle

The single most important design property of the system: **one request returns the entire
history**, and both viewing modes read the same array. Scrubbing back through a circuit is an
array index, not a network call — which is precisely why build mode and playback mode can never
disagree with each other.

```
 Circuit edited            Engine                    steps[]   (len(gates) + 1)
 +--------------+        +--------------+     +------+------+------+------+
 | gates:       |  POST  | evolve one   |     | [0]  | [1]  | [2]  | [3]  |
 | [H, S, H]    | -----> | gate at a    | --> | |0>  |after |after |final |
 | frontend     |        | time,        |     |      |  H   |  S   |      |
 | owns list    |        | capturing    |     +------+------+------+------+
 +--------------+        +--------------+        |                   |
                                                 |                   |
   every snapshot carries:                       |                   |
     statevector[] {re, im, magnitude, phase}    |                   |
     probabilities{}                             |                   |
     bloch{x, y, z, length}                      |                   |
     rotation{axis, angle}                       |                   |
                                                 v                   v
                                    +---------------------+ +---------------------+
                                    | PLAYBACK MODE       | | BUILD MODE          |
                                    | scrubber reads      | | draws steps[last]   |
                                    | steps[k] - array    | | as gates land,      |
                                    | index, no request   | | animated via        |
                                    |                     | | rotation            |
                                    +---------------------+ +---------------------+
                                       one payload, two readers - so they cannot drift
```

**`steps[k]` is the state after the first k gates.** That indexing is what lets the UI scrub
without re-requesting anything. It also makes deleting, reordering or inserting a gate
mid-circuit need no special handling — every edit is just another full re-simulate, which at one
qubit costs microseconds.

### Consequences of this design

- **The backend is stateless.** No sessions, no server-side circuit storage, no incremental
  patching. The frontend owns the circuit and sends the complete gate list every time.
- **Rapid edits overlap.** Dragging an angle slider fires many requests whose responses can
  arrive out of order. Each request carries an incrementing id and any response older than the
  newest applied one is discarded — without this the sphere jumps backwards mid-drag.
- **Sliders are debounced (~60 ms), gate drops are not.** A discrete placement should feel
  instant; a continuous drag should not flood the API.
- **An empty circuit is valid** and returns exactly one step — the initial |0⟩ state that the
  sphere shows on page load.

## 4. Methodology

The development method is **specification-first, backend-first**. A physics simulator that is
merely plausible is worse than useless — a wrong number presented confidently teaches the wrong
thing. So correctness was made falsifiable before any interface was drawn.

### Four stages

1. **Define the contract.** The API shapes, the six concepts, and the gate set were fixed in
   writing first, so the frontend could later be built against a stable target.
2. **Generate golden data.** 104 circuits covering every gate were run through Qiskit and their
   359 state snapshots recorded to `circuits_spec.json` at 6 decimal places. Every rotation
   axis/angle was additionally checked against Rodrigues' rotation formula, so the animation data
   is provably correct rather than merely plausible.
3. **Implement twice, independently.** The production engine and a separate reference engine were
   written against the same spec. Agreement between two implementations and the golden data is
   far stronger evidence than either one passing its own tests.
4. **Build the interface last.** Only once conformance passed was the UI built, against an API
   that no longer moved.

### The verification harness

`conformance_test.py` is the project's real gate — the backend is considered done when it exits
0. It runs against three targets (the production engine, the reference engine, and the live HTTP
endpoint) and checks four families of property.

| Check | What it enforces |
|---|---|
| Structure & golden values | All 104 circuits reproduce their recorded snapshots to 1e-6; `len(steps) == len(gates)+1`; `steps[0].rotation` is null and every later step is not |
| Concept assertions | Reversibility pairs return home exactly; `S·S ≡ Z`, `T·T ≡ S`; interference follows `P(1) = sin²(θ/2)`; a phase gate on a pole moves nothing |
| Teaching content | All eight `explain` fields present and non-empty on every circuit |
| Error handling | Unknown gate, missing angle and Phase-2 gate names each return HTTP 400 with a readable message |

> **Standing rule.** If conformance fails, the backend is wrong. Tolerances are never loosened
> and the specification is never edited to match the code. If the spec genuinely must change, it
> is regenerated from Qiskit rather than hand-edited.

Alongside it, `tests_phase1.py` holds 40 fast unit tests for the same invariants, so the common
case is a sub-second feedback loop rather than a full 104-circuit run.

### API surface

| Route | Returns |
|---|---|
| `GET /api/health` | Status plus catalogue counts |
| `GET /api/gates` | Gate palette with rotation metadata and a reference card per gate |
| `GET /api/concepts` | Six concepts, each with metadata, one canonical preset circuit, and analogy / real-world material |
| `GET /api/concepts/{name}` | One concept plus every circuit that demonstrates it |
| `GET /api/circuits` | Catalogue index — id, concept, label, summary, gate count |
| `GET /api/circuits/{id}` | One circuit's gates plus its curated teaching block |
| `POST /api/simulate` | **The core route.** Runs any circuit, returns a full snapshot after every gate |
| `POST /api/explain` | Teaching content for a hand-built circuit, inferring which concept it demonstrates |

### Response shape

```json
{
  "num_qubits": 1,
  "steps": [
    {
      "step": 0,
      "gate": null,
      "target": null,
      "rotation": null,
      "statevector": [
        { "re": 1.0, "im": 0.0, "magnitude": 1.0, "phase": 0.0 },
        { "re": 0.0, "im": 0.0, "magnitude": 0.0, "phase": 0.0 }
      ],
      "probabilities": { "0": 1.0, "1": 0.0 },
      "bloch": { "x": 0.0, "y": 0.0, "z": 1.0, "length": 1.0 }
    }
  ],
  "final": { }
}
```

Four fields exist for specific reasons and are not redundant:

- `steps` — serves state evolution, and through it every other concept.
- `rotation` — axis and angle per gate. Without it an animation can only interpolate blindly
  between start and end positions, which draws a straight line *through the inside of the sphere*
  and misrepresents the motion.
- `magnitude` + `phase` — phase in radians from `atan2(im, re)`. Phase colouring is the main way
  phase becomes visible; the phase of a zero amplitude is undefined and returns 0.0 by convention.
- `bloch.length` — `√(x²+y²+z²)`. In Phase 1 this is a correctness invariant, since a single-qubit
  pure state always has length 1. In Phase 2 it becomes the visual signature of entanglement. It
  is never normalised.

### Engine internals

The engine evolves **one gate at a time** rather than building a full circuit and reading the
end, because each snapshot must reflect exactly one step. Bloch coordinates come from Pauli X/Y/Z
expectation values on the density matrix; for multi-qubit states a partial trace reduces to the
qubit of interest, which is what makes the Phase 2 extension small.

Rotation axes use a **static per-gate lookup** rather than being derived from the unitary. The
Phase 1 gate set is small and fixed, so a table is simpler and far easier to test:

| Gate | Axis | Angle |
|---|---|---|
| `X` · `RX(θ)` | (1, 0, 0) | π · θ |
| `Y` · `RY(θ)` | (0, 1, 0) | π · θ |
| `Z` · `RZ(θ)` · `P(λ)` | (0, 0, 1) | π · θ · λ |
| `S` · `S†` | (0, 0, 1) | ±π/2 |
| `T` · `T†` | (0, 0, 1) | ±π/4 |
| `H` | (1, 0, 1)/√2 | π |
| `I` | (0, 0, 1) | 0 |

`I` has no meaningful axis at angle 0; a stable dummy is returned rather than null so the frontend
never has to branch, and the rotation is a no-op regardless.

### Teaching content

`explain.py` generates the teaching block from the gate list *plus the actual simulated result*,
never from the gate list alone. Any number quoted in the text — "P(0) is 0.5000", "+45°" — is read
from the simulation that produced the panels beside it. Text derived independently would
eventually disagree with the display, and a physics tool that contradicts itself is worse than one
that says nothing.

Each block carries eight required fields: `concept`, `concept_label`, `concept_intro`, `summary`,
`what_happens`, `watch`, `uses` and `try_next`. The highest-value field is `watch`, because it
names what *does not* move — "the bars are unchanged" is the entire lesson of an `S` gate, and it
is invisible in the plots by definition.

### The simulator screen

Two columns. On the left the circuit strip, the transport controls and the explanation; on the
right the three instruments — Bloch sphere, probability distribution, state vector — stacked so
they read as one panel.

| Element | Behaviour |
|---|---|
| Gate palette | 13 gates, drag or click. Collapses to a rail once the first gate lands, giving the stage more room |
| Circuit strip | Drop anywhere — start, middle, end — with a caret showing the landing slot; chips reorder by dragging and carry their angle |
| Transport | First / previous / play / next / last, a step slider, and `←` `→` `space` |
| Angle control | Docked under the circuit beside the transport, with π/4 · π/2 · π · π/3 · −π/2 presets |
| Bloch sphere | 380 px canvas, drag to orbit, animated along each gate's true rotation arc |
| State vector | Per amplitude: a phase dial, a magnitude bar, and re / im / \|a\| / φ / P |
| Probability chart | Vertical bars with a 0→1 axis and gridlines; zero-probability states still drawn so bars never jump |

### Rendering the Bloch sphere

Hand-drawn on a 2D canvas rather than delegated to a 3D library, which buys exact control over the
two things that make it read correctly:

- **Depth sorting.** Every graticule curve is split at the sphere's midplane and the far half
  drawn at 30% opacity. Without that depth cue a wireframe ball reads as a flat disc.
- **True rotation arcs.** When a gate is applied the vector is swept using Rodrigues' formula with
  that gate's axis and angle, so the path drawn is the path the state actually takes. A straight
  interpolation between two Bloch vectors would cut through the interior of the sphere.

Editing an angle is a different case: no single gate connects the two states, so the vector slides
along the shortest surface arc instead, with the duration scaled to the distance travelled. The
vector is always drawn at its true length, never normalised.

### State management

Circuit history is a stack of gate lists with an index, which gives undo and redo for free and
keeps the frontend the sole owner of the circuit. `useSimulation` computes a local result
synchronously for an instant first paint, then replaces it with the backend's authoritative
answer, applying the stale-response guard described earlier.

> **Resilience.** `quantumEngine.js` is retained as an offline fallback: exact single-qubit
> mathematics, used only when the backend is unreachable, so the interface keeps working with the
> dev server alone. It produces the same per-step structure as the API, because a fallback
> returning fewer steps would collapse the scrubber on every edit.

### The Learn route

Nineteen sections in three groups — six concepts, nine gates plus two overviews, and the full
circuit catalogue — with exactly one on screen at a time. It carries search across all body text,
previous/next paging with arrow keys, reading progress, and an SVG rotation-axis figure on each
gate page. Circuit cards deep-link into the simulator as `?case=P13`, and gate demos as
`?gates=H,T,H`, so a worked example in the text is one click from being a running circuit.

## 7. Physics conventions

- **Angles are radians**, everywhere.
- **Exact simulation** via `Statevector`. No `qiskit-aer`, no sampling — probabilities are
  analytic.
- **All basis states returned** in `probabilities`, including zero-probability ones, so the
  frontend has a stable set of bars.
- **Floats rounded to 6 dp** before serialising, matching the spec's precision.
- **Qiskit is little-endian** — qubit 0 is the rightmost character of a bitstring. Irrelevant at
  one qubit, but bitstring formatting never assumes big-endian.

### Two results that look like bugs and are not

**Global phase is invisible.** `RX(π)` is not exactly `X`; they differ by a global phase factor.
The Bloch sphere is identical, the amplitudes are not — `X` on |0⟩ gives `re = 1.0` on |1⟩, while
`RX(π)` gives `im = −1.0`. Because QubitVista shows amplitudes and the sphere side by side, users
notice and ask. This is correct physics and is left visible deliberately: it is a teaching
opportunity most tools cannot offer, because they hide one view or the other.

**Phase on a pole does nothing.** `RZ` or `S` applied to |0⟩ changes the statevector but produces
no visible change on the sphere and no change in probabilities. Also correct — and it is the setup
for interference: put the phase between two `H` gates and it becomes measurable.

### Worked checks

| Circuit on \|0⟩ | Expected | Spec case |
|---|---|---|
| (no gates) | bloch z = +1, length = 1 | E01 |
| `X` | bloch z = −1 | P30 |
| `H` | bloch x = +1 | S01 |
| `H, H` | bloch z = +1 | S12 |
| `H, S` | bloch y = +1 | P13 |
| `H, Z, H` | bloch z = −1 (HZH = X) | V43 |
| `H, T, H` | P(0) = cos²(π/8) = 0.8536 | — |
| `RX(π)` | P(1) = 1.0 | P32 |
| `RY(θ)` | P(1) = sin²(θ/2) | M04 |

## 8. Phase 2 & limits

Phase 2 adds two-qubit gates — `CX`, `CZ`, `SWAP` — multi-qubit circuits, per-qubit reduced states
via partial trace, correlated measurement outcomes, and entanglement.

Entanglement sits in Phase 2 for a hard physical reason rather than an arbitrary scoping one:
**single-qubit gates are tensor-product operations and mathematically cannot create
entanglement.** They preserve separability. A Bell state requires at least one two-qubit gate, so
entanglement is impossible to demonstrate until `CX` exists.

That constraint shaped the Phase 1 API deliberately. For a Bell state each qubit's reduced state
is maximally mixed, so its Bloch vector shrinks to the origin and the sphere visibly empties —
which is exactly why `bloch.length` is in the response from day one and is never normalised away.

### Out of scope, stated plainly

- Noise and error modelling — the simulation is ideal and exact.
- `qiskit-aer` and real hardware backends.
- Circuit export to QASM or image formats.
- More than one qubit, in Phase 1.

### Honest limitations

- The single-qubit restriction means the most striking quantum phenomenon — entanglement — cannot
  yet be shown.
- Measurement is analytic rather than sampled, so a learner sees exact probabilities rather than
  the shot noise a real device returns. A `shots` parameter is the natural next addition.
- The Bloch sphere is a single-qubit picture; it does not generalise to multi-qubit states, so
  Phase 2 needs a second visual idiom alongside it.
